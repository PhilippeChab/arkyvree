# Development Guidelines

> See [README.md](./README.md) for tech stack, project structure, and setup instructions.

## Code Conventions

- Be DRY
- Reuse existing patterns, naming
- A function in the server, the engine, `shared/`, `database/`, `content/`, `codegen/` or the dev and test seeds (`scripts/db/seeds/`) holds at most 80 of its own lines (`arkyvree/function-length`; blank and comment lines aside, a nested function's body counts in it, not in the function around it): a longer one splits into named steps, helpers above it, never a disable comment. `bun run lint` fails on any disable comment that no longer disables anything
- No comment turns a lint rule off (`arkyvree/no-disable-comments`): a case a rule gets wrong changes the rule, its options or its definition, never one line. TypeScript's errors are fixed, never silenced: no `@ts-expect-error`, `@ts-ignore` or `@ts-nocheck` (`typescript/ban-ts-comment`). An oxlint comment could turn those two off as well, so `tests/lint/disableComments.test.ts` reads every tracked file's comments outside oxlint
- A comment is written one way (`arkyvree/comment-style`; `bun run lint --fix` writes what it can). What describes a declaration is one `/** … */` right above it, and a file may open with one describing the file, a blank line under it (on an import, sorting the imports would move it). In code, a comment is `//`, right above or at the end of what it explains. Nothing stands apart: no heading or banner (`// ── X ──`, a title between `// -----` lines: a section of its own is a module of its own), no comment with a blank line between it and what it describes, no `/* … */`. A comment a tool reads keeps the tool's syntax (`// oxfmt-ignore`, a disable comment, `/*#__PURE__*/`), and so does a JSX comment (`{/* … */}`)
- A body that fits on its statement's line takes no braces (`if (!x) return;`); a longer or nested one takes them, and so does every branch of an if-else chain when one does (`curly`: multi-or-nest, consistent; `bun run lint --fix` writes them)
- An error is named `error`: a `catch`'s binding (or none, `catch {}`), and an `onError` callback's first parameter (`arkyvree/error-names`). A function that only returns a value is an expression arrow, `() => value` (`arrow-body-style`, as needed; `bun run lint --fix` writes it)
- A file's own function is a `function` declaration with typed parameters (`function verbOf(method: string) {…}`, `export async function sendEmailTask(payload: unknown, helpers: JobHelpers)`), never a variable holding an arrow: an arrow is for a callback (`arkyvree/function-declarations`; `bun run lint --fix` declares one)
- State lives in a class (`arkyvree/module-state`): what a module of the server, the engine, `shared/`, `database/`, `content/`, `codegen/` or the dev and test seeds (`scripts/db/seeds/`) keeps between calls (a flag, a lazy value, a counter, a provider it shuts down) is a field of a class whose methods change it, and the module exports the class's shared instance (`export default new Telemetry()`), as a service does. A module's top level holds no `let`, and no binding the module changes (a member assigned or deleted, `++`, a container's `set` / `add` / `push`…): a constant is a value. An `AsyncLocalStorage`'s `run` scopes a callback, and changes nothing
- A value sits above what reads it as the file loads (oxlint's `no-use-before-define`; a read inside a function, which runs once the file has loaded, may point below, as drizzle's tables point their foreign keys both ways, and a function, hoisted, goes by name whatever it calls). A file reads in one order: its imports, its types, its constants, its helpers (the functions it keeps to itself), then what it's for (its exports, its class, a test file's `describe` blocks; an `export default function` or `class` among them), then its export lists and its default export's value (an index's re-exports, `export default new Hono()`), then its run. Within its types, and within its constants, the file's own come first, then the ones it exports. A constant is a value: it never uses the file's own functions or classes (a factory lives in a module of its own, which its values import), and one the file keeps never reads one the file exports. A call, a condition or a loop at a file's top is a step of its run, which only a script has: a module (a file that exports) has none, a script that imports it runs it. Nothing is declared after a step, so its steps go below its declarations, or into a function it calls last (a script's `main()`; a test file's setup, a `beforeAll`). `--fix` never changes the order code runs in: a file with a declaration after a step, or whose order would swap two declarations that run code (a call, `new`, `await`, a class's `extends`, an `export default` value), is reported and moved by hand. A test file's helper never sits in a `describe` (`arkyvree/file-layout`; `bun run lint --fix` orders a file)
- `shared/` holds what more than one of the client, the server and the database packages use, grouped by domain (`customization/`): types and pure helpers, never code tied to one runtime (Bun's APIs, the database; `arkyvree/shared-runtime` refuses `bun` and `node:` imports, there, in `vocabulary/` and in `engine/`), and never a ruleset's. A ruleset's vocabulary is the root `vocabulary/<ruleset>/` (3.5's `vocabulary/dnd3.5/`: its lists, labels, tables and bounds, its property names), data only (`arkyvree/vocabulary-data`: no function or class), which the engine, the client, the content, the codegen and the seeders import directly (the client compiles it in), and the server never does. It never imports `drizzle/schema.ts` at runtime, which would load the whole schema in the client: a database enum's options are written out in `shared/enums.ts`, checked against the schema and the database by `tests/shared/enums.test.ts`. Take the enum types (`ItemLocation`, `ContributorRole`, …) and the customizable entity types (`shared/customization/entities.ts`) from there rather than re-deriving them
- A file's declarations, a class's members, a type's members (an interface's, a type literal's), an enum's members, the names an export lists and an index's re-exports go by name, A to Z (ignoring case), within their groups (`arkyvree/member-order`, `lint/memberOrder.mjs`; `bun run lint --fix` sorts a file, a nested list on its next pass). A type puts its call and index signatures first, in their order, and keeps an overload's signatures together; an enum is sorted only when every member's value is written (an implicit value is its place); re-exports go by the module they're from, a type's after a value's. A file sorts its own types, then the ones it exports, its interfaces together, then its type aliases, in each; its own constants, then the ones it exports; its helpers, then its exports, the sync functions before the async ones in each. What a constant reads goes right above it; a function goes by name whatever it calls (`createSignedInUser` above `signedInApi`, which it calls). `--fix` never swaps two constants whose values run code (a call, `new`): the rule reports them, and `--fix-suggestions` sorts them once nothing depends on the order they run in, as `dev:db:pull` and the parser's generator do. A class goes in groups: its constructor, its static fields, its static methods, its readonly fields, its other fields, its abstract methods (what a subclass gives, so an abstract class reads its contract first), its overrides (what it gives its base), then its private and protected methods, then its public ones; in every group of fields and of methods (static ones too), its private members come first, then its protected ones, then its public ones, so a class's private members stay together. Each group goes by name, methods sync before async (an async method's overload signatures go with it), and a field goes right below a field its initializer reads; `--fix` never moves a field whose initializer runs code (a call, `new`) against the other fields, since what it calls may read any of them; `--fix-suggestions` does, once nothing it calls reads a field the move changes. A router's routes sort by HTTP method, then by path, a fixed segment before a parameter (Hono matches overlapping routes in registration order); a router mounts its sub-routers (`.route()`) first, in their own order, then its routes, which must not overlap theirs (Hono would run the sub-router's first: `tests/routers/application.test.ts` checks every route answers its own requests), and its middleware (`.use()`) comes before them all: Hono applies it only to what's registered after it, so routes that need other middleware are a sub-router of their own (`authentication/`: `signedOut/`, then `signedIn/`, behind the session). The rule is an oxlint JS plugin, in alpha, so oxlint's version is pinned
- A class member that overrides its base's says so, `override` (`arkyvree/override-keyword`; `bun run lint --fix` writes it): TypeScript's `noImplicitOverride` (`tsconfig.json`) requires it of one that overrides a concrete member, and the rule of one that implements an abstract member, which TypeScript leaves unmarked. The rule reads the base chain as `member-order`'s groups need it: `extends X` (its module, by its import), `include(Base, A, B)` (the base and its concerns) and a concern's `Constructor<X>`, through an index's re-exports
- `oxfmt` formats the code (`bun run format`; CI runs `format:check`): 120 columns, the imports sorted and grouped. What tools write is held like the rest, with no exemption: `bun run dev:db:pull` runs `oxlint --fix --fix-suggestions` and `oxfmt` on the schema and relations `drizzle-kit pull` writes, and the parser's generator writes lint-clean code, which it sorts (`member-order`) and formats before swapping `generated/` in. A data table keeps one row per line under `// oxfmt-ignore`. oxlint's `sort-imports` sorts the names inside an import

**TypeScript & Naming:**

- Strict typing enabled
- An object's type is an `interface`, in every package (`typescript/consistent-type-definitions`); a `type` names a union, a mapped type, an intersection or one derived from another (`Omit<…>`, `ReturnType<…>`). An interface has no implicit index signature, so a constraint or a parameter that takes one asks only for what it reads, never a `Record<string, …>`: `CharacterBase`'s components (`C extends { [K in keyof C]: CharacterComponent<D> }`), the path walk's (`object`, a component read by its key with `PathTraverser.findComponent`)
- PascalCase for components/classes, camelCase for functions, 'use' prefix for hooks. In the client, a PascalCase `.tsx` file exports a component of its name (`Card.tsx`: `Card`), or, named in the plural, the family its name says (`FormFields.tsx`: `NameField`, `EmailField`); a camelCase file exports no component; a page is `XPage.tsx` under `pages/` (`XDetailsPage` for a record's own page), and its default export is `export default function XPage` (`arkyvree/component-files`). A hook (`useX`) is the one its own module `useX.ts` is named for, and gives an object (or a single value: `useIsMobile`'s boolean), never a tuple (`arkyvree/hook-files`). A component's own handler is `handleX`; `onX` names a prop (`arkyvree/handler-names`). A module's constant built from a literal (a string, a number, an array or object literal, whatever it holds) is SCREAMING_CASE, and one a style's `sx` takes ends in `_SX` (`arkyvree/constant-names`)
- A module that declares a class and exports it, or its shared instance (`export default new X()`), is named after the class (`arkyvree/class-file-names`): `FeatsService.ts`, `Telemetry.ts`, `References.ts`, `LevelRules.ts`. A module of several classes is named for what groups them (`server/errors/`), and a router's `new Hono()` is another module's class
- Use `@/` path alias for cross-directory imports, never `../`, and import a module of your own folder (or one under it) directly, `./x.ts` (`arkyvree/no-parent-imports`: `bun run lint --fix` rewrites both). A module is imported once, its types inline (`import { type A, b } from "x"`; `import/no-duplicates`), and MUI from its one entry, `@mui/material` (`no-restricted-imports`)
- The server reads its environment through `server/environment.ts`, which lists every variable it reads and what for: `readEnv("APP_URL")`, `isProduction()`, `isTest()`, `isDevelopment()` (`NODE_ENV=development` explicitly: it unmasks errors, so it's never assumed; "not production" is `!isProduction()`). Never `process.env` or `Bun.env` elsewhere in the server, the engine or `shared/` (`arkyvree/environment`); a default stays with the code that reads the variable
- Before finishing a task:
  - TypeScript passes: `bunx tsgo --noEmit -p .`
  - `bun run lint` and `bun run format:check` pass
  - the impacted tests pass: `bun run test:changed`
- Always use Hono's Infer types instead of recreating types in the frontend
- Do not use `any` (`typescript/no-explicit-any`): an untyped value is `unknown`, narrowed by checks (`isRecord`, the engine's `PathTraverser.isTraversable`). A rest parameter may be `any[]`, which TypeScript requires of a mixin's constructor (TS2545, `lib/mixins.ts`); the engine's components are `object`s to the path walk, each read through the getter its path category names (`ComponentSpec`, checked against the ruleset's components) by `PathTraverser.readComponent`

## Backend Architecture

The codebase follows a **3-layer architecture** (Routers → Services → Repositories):

1. **Routes** (`/server/routers`): Hono endpoints that call service methods
2. **Services** (`/server/services`): Business logic, transaction management, error handling
3. **Repositories** (`/server/repositories`): SQL queries (Drizzle ORM), accept `db: Db` parameter

Lint holds the boxes and their layers (`lint/architecture.mjs`) and the method and function names (`lint/methodNames.mjs`):

- **`arkyvree/root-folders`**: each root folder is a box with one role: `client/` the app's pages, which call the server's API; `server/` the API, which stores and transports; `engine/` the rules, which compute over the data they're given; `content/` each ruleset's content, data; `codegen/` the parser, which reads the books and writes the content's generated code; `database/` the content packages' runner and seeders, which write the content into the database. The other boxes may use only the shared surfaces, the engine (through its front door, `arkyvree/engine-front-door`), `shared/` and `vocabulary/`, and the infrastructure, `lib/` (the mixins), `emails/` (the templates) and `drizzle/` (the schema, and what a query runs on, `Db` and `Transaction` in `drizzle/database.ts`), each box what its role reads: only the writers (the server, the database, the scripts) take `drizzle/`'s code, the engine, `shared/`, `vocabulary/` and the client its types alone; the content takes `shared/` and `vocabulary/` alone; `lib/`, `emails/` and `drizzle/` import nothing of the app. The domain boxes (`client/`, `server/`, `content/`, `codegen/`, `database/`) don't reach into each other but by a declared edge, which `ROOT_FOLDERS` names with its reason: the client takes the server's types (its API's, through Hono's typed client), and bundles none of its code; the codegen writes in the content's builders and their seed types (`content/<ruleset>/builders/`: the code it writes is the content's), and reads the core rules' hand-written feats (`content/<ruleset>/data/feats/coreFeats.ts`: a book's aptitudes gather theirs too); the database reads the content's builders, packages and test data (`builders/`, `packages/`, `testData/`: a seeder writes what a package gathers, never `data/` or `generated/` themselves). The tests and the scripts, which run the boxes, import anything: the dev and test data's seeds (`scripts/db/seeds/`: the seed users, each base rules' test characters) are the scripts', since a character's levels and bonded creatures are written as the server writes them. A reach anywhere else means the thing belongs on a shared surface, or is a pipeline step to declare; a new root folder is declared in the table first, or every file in it fails
- **`arkyvree/layers`**: inside a box, a layer imports only what's below it, from `server/database/` up through `server/repositories/`, then copy-on-write's server part (`server/cow/`: its views, `cow/views/`, below its writes, `cow/writes/`), then `server/services/`, `server/jobs/` and `server/routers/`. `server/middlewares/` sits on the repositories, beside the services. `server/cache/` is memoization only, which imports none of the repositories, copy-on-write or the engine. The server stores and transports: it checks access, holds transactions and a generic cache, reads rows and writes them, and asks the engine whatever a ruleset's rules answer. The engine is the root `engine/`: its machinery (`engine/core/`: the evaluators, the path language, the view and copy-on-write, and the module's contract, `engine/core/module/`) sits below the rulesets that run on it (`engine/rulesets/dnd3.5/`), and names none of them, not even for a type. It computes over the rows and the view it's given, and reads and writes nothing: what a save writes is a plan the server writes. So nothing it does waits (`arkyvree/engine-sync`: no `async`, `await` or `Promise` in `engine/`). What it shares with the server, the mixins (`include`, `lib/mixins.ts`), is `lib/`'s, which imports nothing of the app. Copy-on-write's read side, reading and memoizing a ruleset's rows and those its `CowData` is built from (`withRulesetScope`, `RulesetViews`, `RawDataReader`, `CowDataReader`), is `server/cow/views/`; the view they compose into and their `CowData` are the engine's; its write side, the rows a change writes and the copy it makes of an inherited entity (`EntityEdit`, `CustomizationEdit`, `EntityNames`, `EntityCopy`, `CustomizationCopies`, `EntityRepositories`), is `server/cow/writes/`, above it. A ruleset's content is `content/<ruleset>/`: data, which imports none of what reads or writes it, a folder per role. `builders/` is what it's written with (a type per kind of seed, and the functions that write a seed's parts: `feat()`, `simple()`, `classSpells()`), and imports nothing written in it; `data/` the hand-written rows, which no book's page gives; `generated/` what the codegen writes, a folder per book, which wraps no hand-written content; `packages/` each package as data (its name, type and `seedsVersion`, the ruleset it creates, and the content it seeds, gathered from `generated/` and `data/`); `testData/` the dev and test databases' characters. The books' facts its builders and data read (the weapon and armor tables, the skills' and creature types' names) are its vocabulary's. The codegen is `codegen/<ruleset>/` (the parser's tools and the books' reference files): it reads the builders and, of the data, the core rules' hand-written feats, never the generated books it writes nor the packages that gather them; the books' facts it reads (the abilities', saves', skills' and races' names, the core rules' book) are the vocabulary's, and how it reads the books' words (numbers, slugs, a feat family's options) its own (`codegen/<ruleset>/tools/terms/`). `database/` holds what writes: the runner and the registry (`database/packages/`: `RULESET_CONTENT`, keyed by base rules, gives each base rules' core package, extensions, seeder and test characters, and the runner applies the packages in its order), and the seeders (`database/seeders/<ruleset>/`), which read a package's content from its definition, never from `data/` or `generated/`. What every ruleset's content, codegen and seeders share is the core's: `content/core/` (the customization builders, a package's and a test character's shape, the seed types every ruleset's content shares: `FeatSeed`, `RaceSeed`, `ItemSeed`…), `codegen/core/` (the generated folder, the generated code's writer, the HTTP client and page, text) and `database/seeders/core/` (`ContentSeeder`: the seeder's contract, `seedCore`, `seedExtension` and `copyPowerLinks`, a ruleset's seeder implements, and what it runs on: its state, `SeederState`, the steps every ruleset's content seeds alike, `concerns/`, the system rulesets its packages create).
- **`arkyvree/engine-front-door`**: code outside `engine/` (the server, the seeders, the codegen, the scripts) enters it through `engine/index.ts`, as the client enters the server through its API: the class `Engine`, whose handles bind what an operation is about (`Engine.for(scope)` a ruleset's view, and through it `.character(input)`, `.class(klassId)`, `.skills()`, `.modifiers(entityType, entityId)`…; `Engine.forRules(baseRules)` a base rules' content, for the seeders and the codegen; `Engine.copyOnWrite()` what the cache builds the view with), each operation a method taking the data its caller read (a character's rows, a body) and answering data (a description, a plan of writes, a `RulesError` refusal); `RulesError`, the handles' types (`ClassEngine`, `LevelUpEngine`) and each entity kind's rules by table (`EntityKinds`, which `Engine.for(scope).entities(type)` hands out, an operation's arguments read through `Accepted`, as every registered ruleset's takes them), and the types its operations take and answer. Which ruleset answers is the engine's to know, from the ruleset it's handed; nothing else of the engine is exported. The front door is named `@/engine/index.ts`, never the bare folder. A test may reach any of its modules
- **`arkyvree/one-engine-op`**: a service's or a job's action (a method, a function, its callbacks included) asks the engine one operation, however often, through whatever it calls or hands on (its own methods and functions, a handle it keeps, `const levelUp = Engine.for(scope).character(input).levelUp()`, another action's function or service), which answers it whole: a plan carries what it answers once written (its `describe(row)`), a picker its filters, a description everything a page shows. An operation is a method named for a verb that an `Engine` chain reaches (`checkLanguages`, `planCreate`, `describeModifiers`); a noun hands out a handle (`character()`, `entities("skills")`, `levelUp()`), as the entry's own `for`, `forRules` and `copyOnWrite` do. Two operations in one action are a rule the server composes: the engine gets an operation for the action (`character(input).describeForMember`, a partial reading or the sheet). The cache isn't an action: it builds the view, and keeps what the engine lists of it (`RulesetViews.getTargetPaths`)
- **`arkyvree/opaque-view`**: the server holds a ruleset's view only as the scope `withRulesetScope` gives it, which it binds the engine to (`Engine.for(scope)`): of its `rulesetData`, it reads the copy-on-write data alone (`rulesetData.cow`: the source chain its reads filter by, what `EntityNames` and `CustomizationEdit` check and write by), under its own name, and never asks the cache for a view (`RulesetViews.getData`, under any name). What the view answers, an operation answers; the cache builds the view, and keeps what the engine lists of it, a ruleset's target paths (`RulesetViews.getTargetPaths`, `getTargetPathCatalogs`)
- **`arkyvree/engine-classes`**: inside the engine, each area is a class, or a few around a base and its concerns (the level-up's `LevelUpState`, on core's `LevelUpBase`): its public methods are what it answers (`LevelsPlanning.planLevels`, `FeatPicker.annotate`, `ItemEntity.planVariants`), its steps its private methods, its concerns' or its module's own functions. Its entry is classes too (`engine/api/`): `Engine` and the handles it hands out (`RulesetEngine`, `CharacterEngine`, `LevelUpEngine`, `ClassEngine`…; an entity kind's own class, on `RulesetEntity`, which `entities(type)` hands out), each operation a method that asks the ruleset's module (`Modules.of(baseRules)`) or the core's classes. A module exports no function of its own (declared, held by a const, or listed), so no file reaches into another's steps: it exports classes (their statics for what several areas read, `PathTraverser.readComponent`, `LiteralValue.parse`), concerns, components, types and data
- **`arkyvree/queries-in-repositories`**: a query (`db.select`, `tx.update`, `db.query.…`, `unionAll`) is built in `server/repositories/` or `server/database/` (what talks to Postgres itself: the job queue's `addJob`, `notifyChannel`, `pingDatabase`), nowhere else in the server. A transaction's handle is named `tx` (`withTransaction(async (tx) => …)`), the name the rule knows a query by
- **`arkyvree/folder-index`**: code outside a folder that has an `index.ts` imports it through that index: every server and engine folder that has one (the services', `cow/`, `policies/`, the repositories', the database's, the cache's, the engine's, the emails'…), but the routers' (a route folder's `index.ts` is its routes), and the client's component folders, which code outside enters at their outermost index, and a ruleset's code enters a folder of its own ruleset at that folder's index (`components/characters/sections/dnd3.5/index.ts`), which the generic folder around it re-exports none of. Files within the folder import each other directly; a test may reach a folder's own modules, and so may the seeders, the codegen and the scripts, though they enter the engine through its front door (`arkyvree/engine-front-door`)
- **`arkyvree/ruleset-folders`**: a ruleset is a folder of `engine/rulesets/`, and every folder of its name, in any tree, is its own (`content/<ruleset>/`, `codegen/<ruleset>/`, `database/seeders/<ruleset>/`, `vocabulary/<ruleset>/`, the client's and the tests'). A ruleset's code imports none of another's; what every ruleset runs on (`engine/core/`, `content/core/`, `codegen/core/`, `database/seeders/core/`, the runner, `database/packages/`, the scripts, the dev and test seeds among them, the server, `shared/`, `lib/`) names none of them. A registry (`engine/api/Modules.ts`, `database/packages/registry.ts`, the client's factories) and a test may name any ruleset: the runner and the scripts reach a ruleset's packages, seeder and test characters through the content's registry alone. A client module outside a ruleset's folder reaches a ruleset's code and vocabulary through the client's registries alone, each keyed by base rules (`getSections`, `getLevelWizards`, `getVocabulary`, `getClassForms`…: `CLIENT_REGISTRIES` in `lint/architecture.mjs` lists them), never from its folders: a type it reads comes from the API (`InferResponseType`)
- **`arkyvree/re-exports`**: an `index.ts` that re-exports is its folder's entry, and only re-exports (`export { x } from "./x.ts"`): its own code goes in a module named for it (`database/connection.ts`, `repositories/instances.ts`). Any other module exports what it declares, never another module's (no `export { x } from`, no export list of what it imports): code that needs it imports it from where it's defined (`parseResponse` from `hono/client`, `Sentry` from `@sentry/bun`).
- **`arkyvree/method-names`**: a public method starts with a verb its layer knows. A repository reads with `find`, `exists` or `count`, writes with `create`, `update`, `upsert`, `delete`, `archive`, `unarchive`, `mark`, `backfill`, `orphan` or `publish`, and locks with `lock`: `server/repositories/methodVerbs.json`, which the request cache classifies its methods by (a read is memoized within the request and sees copy-on-write ids, a write clears the cache). A service reads with `get`, creates with `create`, `add` or `duplicate`, updates with `update`, `set` or `mark`, deletes with `delete`, `remove`, `archive`, `unarchive` or `hardDelete`, or takes one of the actions `lint/methodNames.mjs` lists (`fork`, `publish`, `invite`, `accept`…), on its own resource: `FeatsService.getFeat` / `getFeats` / `createFeat`, `CampaignPlayersService.addPlayer`, a class is `Class` (`ClassesService.getClass`; `Klass` stays in the schema). Never `ById` (the id is a parameter) or `My` (the session's scope is implied). A policy checks with `can` (it throws, or returns what it checked) or `is` (a yes or no), and `for` builds one. A repository method never names a filter (`By`, `For`, `In`, `On`, `From`, `All`): its filters go in its `where`. Private and protected methods name themselves
- **`arkyvree/function-names`**: an exported function of the server, the engine, `shared/`, `database/`, `content/`, `codegen/` or the dev and test seeds (`scripts/db/seeds/`) (declared, held by a `const`, or listed in an `export { f }`) starts with a verb (`FUNCTION_VERBS` in `lint/methodNames.mjs`: `describeCharacterCards`, `readCharacterInput`, `compareInConstantTime`, `writeEntityWrites`), or is one of the shapes the code writes: a context it runs a callback in (`withTransaction`), an event's handler (`onCacheHit`), a conversion (`toSafeUser`) or a constructor (`newTimingStore`). A PascalCase one names a type (a concern, a class's factory), and a module's own functions name themselves. A ruleset's content builders (`content/<ruleset>/builders/`, and those every ruleset's share, `content/core/builders/`) are the vocabulary its data is written in (`eq(feat("Dodge"))`, `simple("Club")`), named for what they build.

Where code goes, by what it needs:

- A step only one class takes, and small: a `private` method of that class
- Methods that work on a class's state (`this`), split out of a large class or shared among classes of one kind: a concern, a mixin the class includes (`include(Base, A, B)`, `lib/mixins.ts`), in a `concerns/` folder by the class. It's named for what it adds, in a file of its name: a verb when it adds behavior (`Archives`, its class `Archiving`), a noun when it adds a part of the model (`ArmorClass`, its class `WithArmorClass`). It adds methods, never state (`arkyvree/concern-shape`)
- A function that needs no `this`, used by several services, jobs or tests: a helper, a module named for what it does (`characters/editableCharacter.ts`), in the folder of the service whose domain it is, exported through its `index.ts`. Never a `helpers` or `utils` grab bag (`arkyvree/no-helpers-modules`)
- A query: a repository method (a query across every entity table: `RulesetEntities`)
- A ruleset's rule (what its characters, entities, level-ups or content answer): an operation of its module (`engine/rulesets/<ruleset>/`), which the entry's handles dispatch to (`engine/api/`: `Engine`, exported by `engine/index.ts`). The server reads what it takes and writes what it plans, never computes it

**Key Patterns:**

- Every write (create, update, delete) and lock goes through a transaction: a repository write or lock outside the repositories takes its handle, `tx` (`withTransaction(async (tx) => …)`), never the shared `db`, in the services and the jobs alike (`arkyvree/writes-in-transactions`, by `methodVerbs.json`'s write and lock verbs). A transaction's queries run one at a time, on its one connection: await them in turn, never in a `Promise.all` (the rule reports one over `tx`, or over a handle a function is given, which may be a transaction; node-postgres queues them today and pg@9 throws)
- Repositories accept `db` via dependency injection
- Schema is defined in `/drizzle/schema.ts`
- Routes validate with `validate` from `@/server/middlewares/index.ts` so validation failures use the standard API error envelope and preserve Hono response inference (`arkyvree/route-conventions` holds it, camelCase path params, kebab-case fixed segments, a status on every `c.json`, and no `try` in `server/routers/api/`).
- A route's params are a named schema, never written in the route (`validate("param", featParams)`; `arkyvree/route-conventions`): the ones several routers use come from a `validation.ts` (`server/routers/api/validation.ts`: `idParam`, `characterIdParam`, `contributorParams`; the class routes' `classParams` from `rulesets/classes/validation.ts`, the customization routes' `entityParams` and `ownerParams` from `rulesets/customization/validation.ts`), and a router's own are declared at its top, built on those (`const featParams = idParam.extend({ featId: z.string().uuid() })`). Paging comes from `server/routers/api/validation.ts` too (`page`, `limit` / `limitDefaultingTo(n)`). A query list (comma-separated ids, picks) is parsed by its schema's `transform`, not in the handler. Path params are camelCase (`:modifierId`), and fixed segments kebab-case (`/class-levels`, `/spells-known`). A URL says "class" where the code says "klass" (`class` is a reserved word): an entity type in a path or a query is its segment (`getUrlSegment` in `shared/urlSegments.ts`: `class-levels`, `classes`), which a route reads back as the type with `buildEntityTypeSchema`, and a query names a class `classId`. The schema, the services and the JSON bodies keep `klass`
- A route's body and query are written in the route (`validate("json", z.object({ name: z.string().min(1) }))`), or at its router's top when several of its routes take one, as it is or derived (`itemBody.partial()`), named for it (`itemBody`, a query's `…Query`); a field schema several bodies share is named for its value (`hitDie`, `levelSaves`), never `…Schema` (`arkyvree/route-conventions`). An account's text (an email address, a username, a password, a code) and an invite's email address are sanitized as they're stored (`sanitizedText`, `sanitizedEmail` from `server/routers/api/validation.ts`: trimmed and Unicode-normalized, by `shared/text.ts`'s `sanitizeText`, which the client's rules measure with too), and a check chained to one reads the sanitized text (`sanitizedText.min(3)`). The handler reads its input into a const and destructures what it reads (`const { id } = c.req.valid("param")`, `const { name } = c.req.valid("json")`), or names an input it hands on whole `body` or `query`. A router is its module's export: `export default new Hono()…`
- A body's fields that a ruleset's rules take, and their bounds, are the engine's: a route carries an entity's fields as one object, `fields` (`buildEntityFieldsSchema<EntityKinds["skills"]["planCreate"]>()` from `server/routers/api/schemaBuilders.ts`, any object, typed as the engine takes it so the client's forms keep their types), which the operation reads by the kind's codec, and a column a rule bounds as its type alone (`level: z.number().int()`, `hd: hitDie`). The operation refuses a field or a column past its rules with a `RulesError` "invalid" (`RulesError.parse`), which answers 400 with an issue per field, as the route's validation does (`fields.bab`, `saves.0.base`). The server imports nothing of `vocabulary/dnd3.5/`
- A route answers with what its service returns: `return c.json(await XService.method(…), status)`. What a route or a service throws reaches the app's `onError` (`server/routers/application.ts`; `wrapNonErrors` makes a thrown value that isn't an `Error` one first), which answers with the error in the API's envelope and its status. The engine throws no HTTP error: a rule refuses with a `RulesError` (`engine/core/RulesError.ts`) naming its kind (`invalid`, `unprocessable`, `conflict`, `not-found`), which `toJson` answers as the server's error of that kind: a route never catches a service's error to answer it. So a route's types list its successes only, and a test checks an error status with `expectStatus(response, status)` (`tests/support/api.ts`).
- A ruleset's rules are the engine's, never the server's: a service reads the rows an operation of `Engine` (`engine/index.ts`) takes (its scope's view, a character's input: `readCharacterInput`), asks it (`Engine.for(scope).character(input)…`), and answers the description it gives or writes the plan (an entity's create, edit or delete through its kind's `EntityWriter`, which writes its `EntityWrites` with `writeEntityWrites`; the bonded creatures' with `writeBondedCreatures`). See [docs/rulesets.md](./docs/rulesets.md#universal-vs-ruleset-specific-code)
- A response never carries a user's `passwordDigest`. Auth responses return the user through `toSafeUser` (`server/services/authentication/accounts.ts`), and a query that joins users selects their public columns (`id`, `username`, `emailAddress`), never the whole row.
- `deletedAt IS NOT NULL` means **archived**. The codebase has two row-removal primitives — `repo.archive()` (soft) and `repo.delete()` (hard). Which one to use depends on the table. See [docs/persistence.md](./docs/persistence.md) for the full policy and decision rule. Quick rule: first-class user-facing entities archive by default; junctions, character-state, and customization rows always hard-delete.

**Service Conventions:**

- Session parameter is always named `session: Session`, never `s` (`_session` when it's unused; `arkyvree/session-param`)
- Use **individual parameters**, not payload/options objects: `linkCharacter(userId, campaignId, characterId, visibility)` not `linkCharacter(payload)`
- Use **shared repository instances** from `@/server/repositories/index.ts`, never instantiate private copies (`arkyvree/repository-instances`). `withRequestCache` (`server/repositories/withRequestCache.ts`) wraps each one there. The repositories sit in folders by domain, like the services' top-level folders (`repositories/rulesets/FeatsRepository.ts`)
- Paginated service methods follow: `method(id, where: { search?, orderBy?, orderDir? }, pagination: { limit, page })`
- A service is a class used through its one shared instance, like a repository: its file exports `new XService()` and nothing else. Routers and tests call its methods on it (`XService.method(…)`), never detached, which would lose `this` (a test that passes one as a value binds it)
- Each service has a folder of its own, laid out like the routers (`rulesets/feats/FeatsService.ts`, `characters/inventory/CharacterInventoryService.ts`). A helper only that service uses is one of its `private` methods, at the top of the class, or a module in its folder when it's large (`extensions/departingReferences.ts`, the level flows in `characters/levels/`). A helper several services use is a module in the folder of the service whose domain it is (`characters/editableCharacter.ts`, `characters/pdf.ts`, `activities/activityNotifications.ts`), named for what it does, never a `helpers.ts`. A folder's `index.ts` exports its service and what code outside the folder uses from it: code outside imports through it, files within the folder (its subfolders included) import each other directly
- A large service splits by concern, the way Ruby includes a module: a concern is a mixin in its folder's `concerns/` (`rulesets/concerns/Publishes.ts`), and the service includes it with `include(Object, Archives, Publishes, Stars)` (`lib/mixins.ts`), its concerns by name (`arkyvree/include-order`). A concern adds methods, never state, and builds on the class's base alone; a helper it shares with the class is `protected`, and one several concerns share belongs to the base (`CombatState`) or a module. So does a large character engine class (`CombatComponent` includes `combat/concerns/`: `ArmorClass`, `Attacks`, `HitPoints`…). A class with state to split keeps that state in a base its concerns build on (`CombatState`, `SpellcastingState`). So does a policy: `RulesetsPolicy` is `RulesetRoles` (the session's role on the ruleset) plus `policies/concerns/` (`ContributorRights`, `CreationRights`, `EntityRights`, `ExtensionRights`)

**Permission Checks (Policy vs. Identity):**

Permission gates that determine whether a session is _allowed_ to perform an action belong in a Policy class under `server/services/policies/` — `CampaignsPolicy`, `CharactersPolicy`, `RulesetsPolicy`, etc. Each has the checks its services make (`canUpdate`, `canDelete`, `canManageContributors`, `canPublish`, …): a check no service makes doesn't exist. Policies throw `ForbiddenError` / `UnprocessableEntityError`; services call them and let the throw propagate.

A service builds a policy with `await XPolicy.for(db, session, entity)`, never `new`, and its checks are sync (`arkyvree/policy-shape`): see [docs/access.md](./docs/access.md) for what `for` loads and what a check is passed.

Inline `<x>.userId === session.userId` comparisons are only acceptable when they're **identity matches**, not permission gates:

- "Is this invite addressed to me?" — `invite.userId !== session.userId` in the invite services' `acceptInvite`
- "Did I just oauth-link this account to myself?" — `existing.userId === session.userId`
- "Am I removing my own player slot?" — `isSelfRemoval = player.userId === session.userId` (a branching predicate, not a gate)
- Boolean predicates an attachable record registers — the `isOwner(session, recordId)` of `ATTACHABLE_TYPES`' entries (`server/services/attachments/AttachmentsService.ts`): an avatar's `session.userId === recordId`, a portrait's `character.userId === session.userId`

Anything that _throws_ on the basis of ownership is a permission check and should move into a Policy.

**Repository Conventions:**

- `where` params use **union types** for type safety, not all-optional objects: `where: { id: string } | { userId: string; campaignId: string }`
- One method per verb: a repository's `findOne`, `findMany`, `findPage`, `exists`, `count`, `create`, `update`, `delete`, `archive`, `markRead`, `lock`… each take a `where` union of every filter they serve (`delete(db, { klassLevelId } | { featId } | { aptitudeId })`, `archive(db, { id } | { userId })`), never a `findManyByX` / `deleteByX` / `archiveAllForX` sibling: `arkyvree/method-names` reports a name with a filter word (`By`, `For`, `In`, `On`, `From`, `All`). A variant exists only when its result differs, named by that result (`countPerRuleset`, a Map). When a union's branches run different queries, the public method dispatches to a private method per branch
- Use `this.where([...])` with `"key" in where && eq(...)` to build conditions from union types
- A query whose `where` is a union builds its WHERE with `this.branchWhere(keys, rest)`: `keys` are the conditions that pick its rows, one per branch, `rest` those that narrow them (`isNull(deletedAt)`, `rulesetId`, `status`). A `where` that matches no branch throws, instead of a write reaching every row or a read returning any
- An empty list never reaches the database, and is checked in one place: a read that filters on a list of its `where` (`inArray(column, where.ids)`, outside an `or`) answers an empty one first, without a query (`if (where.ids.length === 0) return [];`, `undefined` for a `findOne`, `this.paginated([], pagination)` for a page), so its callers read without checking (`arkyvree/empty-list-reads`). A write skips an empty list in its repository too (an insert of no rows throws)
- A read says it found nothing with `undefined`, as drizzle does (`findFirst`, `const [row] = …`), never `null`, which is a column's empty value: no `?? null`, no `| null` return type (`arkyvree/no-null-reads`). A response says none with `null`, since JSON leaves an undefined key out, so a service converts where it builds the response (`contributorRole: contributorRole ?? null`)
- A read is named by what it returns: `findOne` a row, `findMany` an array, `findPage` a page (`findPage(db, where: { ...filters, search?, orderBy?, orderDir? }, pagination: { limit: number; page: number })`). A read whose result has another shape says which: `findOneWithBlob` (a row and its blob), `findOptionPage` (a picker's options), `findIds`, `findRole`
- Pagination goes in a **separate `pagination` param**, never mixed into `where`
- `BaseRepository` holds a repository's core (`table`, `where`, `branchWhere`, `visibility`, `orderBy`, `lock`). Everything else is a concern in `server/repositories/concerns/`, a mixin the repository includes when it uses it, the way Ruby includes a module: `class CampaignsRepository extends include(BaseRepository<typeof campaignsInCampaign>, Paginates, Searches)` (`include` from `lib/mixins.ts`). The concerns are `Paginates` (`paginate`, `paginated`, `withPagination`; the `Paginated` type, `paginateItems`, and `fetchEveryPage` for every page of a `findPage`), `Searches` (`search`, `fuzzySearch`, `searchOrderBy`), `ScopesToRuleset` (`buildRulesetCondition`, `RulesetEntityFilters`; the repository names its `entityType`), `ChecksRulesetUse` (`rulesetOrDescendant`), `ResolvesCopies` (`idMatches`, `excludeIds`), `GuardsStaleEdits` (`casUpdatedAt`) and `ChecksExistence` (`exists`, through `findOne`). A concern adds methods, never state
- Use `this.withPagination(pagination, callback)` for paginated queries. For join queries that return non-model types, use `this.paginate()` / `this.paginated()` directly
- Use `this.search(search, [columns])` for text search — returns `SQL | false`, use `|| undefined` when passing to `and()`
- Use `this.orderBy(column, direction)` for sorting — never hardcode `desc()`/`asc()` directly (`arkyvree/order-through-repository`)
- A paged read orders by `this.pageOrder(keys)` (`Paginates`), which ends on a key no two rows share: the table's id, or a group's own (``pageOrder(key, sql`min(id::text)`)``). OFFSET paging runs one query per page, and rows that tie on every key would repeat or go missing across pages (`arkyvree/order-through-repository`)
- A read copy-on-write's views compose a ruleset's view from (`RawDataReader`, `CowDataReader`, `RulesetViews`) orders its rows, so the view never depends on the plan: rows a page lists in the order they were made (`createdAt`), a tie broken by the row's own key (a property's type and value, a requirement's level, a modifier's target and id, a feat's or a spell's list links by list); ids and pairing inputs by their key (`findLeveledIds`, `findNativeNames`)
- Search sentinel is `false` (not `undefined`) for consistency with `this.where()` filtering
- A query across every ruleset entity's table is a `RulesetEntities` method (`repositories/rulesets/RulesetEntitiesRepository.ts`; `entityTables.ts` maps each type to its table and lists `RULESET_ENTITY_TYPES`). A repository reads rows as stored, and a query takes the ids it's given: what it needs of copy-on-write it's handed from its scope's `rulesetData.cow` (a list's `listFilters`, an entity's `getEquivalentIds` for stored rows, the id one `resolve`s to), and the engine reads the rows it's handed as the view does (`CharacterInputs`, an entity kind's list, `openList`)
- A ruleset entity's repository extends `RulesetEntityRepository` (its `create` / `update` / `delete`, and the concerns every entity's list and edit use: `Paginates`, `Searches`, `ScopesToRuleset`, `GuardsStaleEdits`) and types its list's `where` as `RulesetEntityFilters<{ …its own filters }>`. Its list leaves out the scope's sibling losers in the query (`ScopesToRuleset`, given `rulesetData.cow.listFilters`), so no service filters them, and a list's composed links (`featsAptitudesInRules`) are the engine's: its list operation's `describe` gives a page's rows them (`entities("feats").openList`, `entities("powers").openList`). A bulk insert is `createMany(db, rows[])`. An in-use check joins the character's ruleset with `this.rulesetOrDescendant(column, rulesetId)`
- A level's rows' repositories (its picks', `CharacterLevelSkills` / `Feats` / `Powers`, and its ability increases', `CharacterLevelAbilityIncreases`) extend `LevelPicksRepository` (`repositories/characters/`): its in-use checks by column (`existsPick`, `existsPickFromExtension`), `createMany` and `delete`; each keeps its `findMany`, by the picked entity's name, and a pick's its `exists` dispatch

## Testing

**Guidelines:**

- Never skip failing tests or use mocks (`arkyvree/test-conventions`: no `.skip`, `.only`, `.todo`, `.fixme`, `.if` / `.skipIf`, no `mock` / `spyOn`)
- A `bun:test` `expect` is never awaited, `.resolves` / `.rejects` included: Bun's matchers are synchronous (those two block until the promise settles, and throw), and its types have them return `void` (`arkyvree/sync-expects`; `bun run lint --fix` drops the `await`). Such an `await` only yielded a tick: a test that needs one awaits what it waits for by name (`await promise.catch(() => undefined)`, once that promise's own handlers must have run). Revisit on a Bun upgrade whose types have a matcher return a promise: the rule then flips back for it, or a failing test would pass unnoticed. Playwright's `expect` (`tests/e2e/`) is another import, whose web-first assertions (`toBeVisible`, `toHaveText`…) wait, so they keep their `await`
- Use seed data from test database
- Run with `bun run test`, or `bun run test:changed` for the files changed from the parent branch
- E2E (`bun run test:e2e`) builds the client for production and serves it with the API from one server on port 8010 (`E2E_PORT`), on a database of its own (`<name>_e2e_<port>`): a copy of the e2e template (`<name>_e2e`), which `bun run test:db:reset` copies from the seeded test database, so a run never locks the unit tests' database. It runs on half the CPU cores locally; pass `--workers N` to change it for one run. `E2E_SKIP_BUILD=1` reuses the last build; `E2E_COVERAGE=1` reports the client code the journeys run (coverage/e2e)
- E2E setup goes through the API (`signIn`, `forkCoreRuleset`, `createCharacter`, `createCampaign`, or `apiOf(page)` from `tests/e2e/support/api.ts`): a journey clicks through only what it tests. Select by role and accessible name, never by `data-testid` (the production build strips MUI's). Every e2e file imports `test` from `tests/e2e/fixtures.ts`, and `expect` from `@playwright/test` (`arkyvree/test-conventions` holds it)

**Test Structure:**

- A test named after a module sits at that module's mirror (`arkyvree/test-placement`): `tests/services/campaigns/invites/CampaignInvitesService.test.ts` tests `server/services/campaigns/invites/CampaignInvitesService.ts`, `tests/vocabulary/dnd3.5/spells.test.ts` tests `vocabulary/dnd3.5/spells.ts`. A test of a behavior across modules is named for it, in its area's folder (`tests/services/rulesets/EntityServices.test.ts`, `SiblingSemantics.test.ts`)
- Backend tests: `/tests/routers` (the API, through `tests/support/api.ts`), `/tests/services`, `/tests/engine` (the engine: its machinery, its operations, and the 3.5 module's characters, target paths, requirements, level-ups and sheets), `/tests/cache`, `/tests/seeds` (the seeders, the seeded content, the package runner and the test data), `/tests/codegen` (the codegen, mirrored: its core's tools, `tests/codegen/core/`, and each ruleset's, `tests/codegen/dnd3.5/tools/`; the scraper's pages read the trimmed pages in `tests/codegen/dnd3.5/fixtures`, through `tests/support/dnd3.5/scrapedPages.ts`), `/tests/jobs`, `/tests/middlewares` (the rate limits, `wrapNonErrors`), `/tests/emails` (the email service and its templates), `/tests/shared` (the shared code, and its enum and operator lists against the schema and the database), `/tests/vocabulary` (a ruleset's vocabulary), `/tests/scripts` (the database scripts' guards, and `prod:diff`'s content comparison: every column of every seeded table), `/tests/lint` (the repo's own lint rules, and `documentation.test.ts`: the docs name every rule, shared component and hook), and `tests/environment.test.ts` (`server/environment.ts`'s Fly variables against [docs/deployment.md](./docs/deployment.md)'s table)
- Client tests: `/tests/client` (the client's logic that needs no browser: `lib/`, the stores' and services' pure modules, and a component's or a page's, such as the inventory dialogs' `equipment.ts` or the level wizard's `levelUp/` rules)
- E2E tests: `/tests/e2e`; `/tests/fixtures` holds Playwright's environment, global setup and teardown and auth fixture, and the document `scripts/check-pdf-bundle.ts` renders
- What every test shares: `/tests/support` (below), `tests/setup.ts` (each backend test's transaction, the fake storage) and `tests/env.ts` (`NODE_ENV=test`), both preloaded by `bunfig.toml`
- What tests do differently (no CSRF check, rate limit or email, cheap password hashes) reads `isTest` (`server/environment.ts`): `NODE_ENV=test`, which `tests/env.ts` and the e2e server set, never the database's name
- Each test runs in its own transaction, rolled back afterwards (`tests/setup.ts`); a transaction the code opens in it (`withTransaction`, `db.transaction`) is a savepoint on the same connection, rolled back when it throws. In production that transaction is its own, on another connection, so tests don't catch transaction-boundary bugs (what it can see, when it commits). It has a single connection: run service calls that write one at a time, never in a `Promise.all`: concurrent savepoints share a name, so one's failure silently undoes the other's writes
- The ruleset cache outlives the rollback. Write a test's rows into a fork (`createSeededTestRuleset`), not a seeded ruleset; a test that has to write into a seeded one calls `invalidateSeededRuleset(rulesetId)` afterwards, and the setup drops those rules again once the rollback undoes the rows
- CRUD, ownership and copy-on-write of every ruleset entity are tested once, for all of them, in `tests/services/rulesets/EntityServices.test.ts`: an entity's own service test covers only what's particular to it

**E2E directory → Playwright project mapping:**

The directory a new e2e file lives in determines which `project` it runs under. Get this wrong and the file won't be picked up.

- `journeys/` → `journeys` project: every signed-in test. Each signs in itself through the API (`signIn`), as users of its own from `tests/e2e/fixtures.ts`: the worker's `ownerUser` / `inviteeUser` for tests that build their own content, and the test's own `user` for one that changes the user itself (email, password, session, stars), so no test depends on another's order or leftovers. `seedUser`, the seeded characters' owner, is for tests that only read them.
- `auth/`, `navigation/unauthenticated-redirect.e2e.ts` → `guest` project: signed out. Sign-in / sign-up / forgot-password / pre-auth redirects.

Adding a brand-new directory? Update the regex in `playwright.config.ts` (the `testMatch` for the relevant project) — otherwise the files won't run.

**Selector gotchas captured by existing tests:**

- A `Typography` sized as a heading declares its element (`arkyvree/headings`): `component="h3"` renders `<h3>`, matched by `getByRole('heading')`, and `component="p"` a paragraph, which text-based selectors find.
- Scope dialog selectors to the open MUI dialog with `[role="dialog"][aria-modal="true"]` or by accessible name: `page.getByRole('dialog', { name: 'Fork Ruleset' })`.
- A page's action menu item (`ActionMenuItem`) is one line, its accessible name its label: `menuitem` named `/^Fork$/`, `/^Delete Permanently$/`. A list option with a second line (`<ListItemText primary secondary />`, a picker's) is named by both lines: match its first with `/^Name\b/`.
- Filter and sort options live inside popup `<Menu>` components; click the "Filter"/"Sort" tooltip IconButton first, then the `MenuItem`.
- Submit-button labels go by dialog wrapper: `CreateDialog` → "Create", `EditDialog` → "Update", `DeleteDialog` → "Delete"; a dialog whose action is its own names it (Fork Ruleset, Archive Campaign, Send Invite), and an "Add …" one submits its words (Add Player, Add Modifier, Add Item). A create dialog's title is "Create New …" (but "Add Player", "Add Modifier", "Add Item to Inventory", "Create Requirement", "Fork Ruleset"), an edit dialog's "Edit …". Check the actual component before writing the assertion.

- `characters.ts`: a character written straight to the database (`createTestCharacter`), created through the service (`createCharacterAs`) or through the API (`postCharacter`), built as the engine builds it (`buildCharacter`: its rows read as the server reads them, `readCharacterInput`, built by its base rules' module); `levels.ts`: class levels and a character's (`createTestKlassLevel`, `findKlassLevel`, `addCharacterLevel`, `addOneLevel`), a character that picked a feat (`pickFeat`)
- `dnd3.5/`: 3.5's own: `characters.ts` (`buildAs`: a character built as the 3.5 class a test reads it as, a familiar's, a mount's…, refused when its row's kind builds another), `levelFixtures.ts` (seeded character builds, level plans and level-ups, and masters with their bonded creature) and `scrapedPages.ts` (the scraper's trimmed pages)
- `database.ts`: `insertRows(table, rows)` for bulk setup, what a callback costs the database (`measure`: its queries and cache hits), a call that must wait on another transaction's lock (`runWhileLocked`); `activities.ts`: a row's `activityTypes`; `jobs.ts`: what was queued (`queuedJobs`, `queuedPdfJobs`), `silentJobHelpers`; `files.ts`: `createExport`, `createTestAttachment`; `storage.ts`: the fake storage backend
- `api.ts`: the typed API client as the seed user (`api`), a guest (`guestApi`) or a new user (`createSignedInUser`), `expectOk` (a 2xx response's body) and `expectStatus` (an error's status)
- `tests/seeds/seededRows.ts`: a seeded ruleset's own rows, for the seed tests; `tests/seeds/freshSeed.ts`: a new system ruleset (or extension) for a seeder test to seed into, and what an entity was seeded with
- `tests/e2e/support/`: signing in (`signIn.ts`: `signIn`, `signedInPage`, the form's `submitSignIn`, and `openContext` for another user's or a guest's context, which the run's coverage records), `characters.ts`, `campaigns.ts` and `rulesets.ts` (`createCharacter`, `createCampaign`, `forkCoreRuleset`, all through the API, and the pages they open), invites (`invitePlayer`, through the API `postPlayerInvite`, `inviteContributor`, `answerInvite`), `page.ts` (`uniqueName`, since ruleset names are unique across users, `openActionsMenu`, `filterList`, `apiResponse` waits), `emails.ts` (verification and reset codes, OTP, signing up), `notifications.ts`, `levelUp.ts` (the Add Level wizard) and `api.ts` (`apiOf(page)`). They scope dialog interactions to `[role="dialog"][aria-modal="true"]`; the seeded users' credentials are `TEST_USERS` in `tests/fixtures/auth.fixture.ts`
